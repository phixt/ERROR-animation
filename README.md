# ERROR-animation

模拟恐怖（analog horror）风格的终端艺术。素材取自这台机器近 30 天的 Windows
服务控制管理器（SCM）崩溃日志 —— 不是编的，是真实记录的官僚式遗言。

画面是一台没人管的机器在反复自我抢救：**错误 → 修正操作 → 重试 → 又失败**，
进度条一次次走不到头，直到最后只剩黑屏、一个光标，和「未检测到任何用户。」
—— 然后是一记跳杀。

---

## 快速开始

```bat
run.bat                          :: 终端播放（双击也行）
run.bat --speed 4.0              :: 4 倍速速览
run.bat --scene 5                :: 从第 6 段开始
run.bat --audio                  :: 开音频（恒定噪声 + 红黄警告音）
run.bat --interactive            :: 允许真的按 Y/n 回答重试提示
run.bat --random on              :: 打开随机机制，背景噪声与额外错误从语料库采样
run.bat --no-jumpscare           :: 去掉结尾的跳杀

film.bat                         :: 出片 -> out\demo.mp4（含音轨，四步全自动）
film.bat --fps 60 --crf 16       :: 60fps、更高质量
film.bat --no-crt                :: 干净版（不做 CRT 后期）
film.bat --bands 0               :: 关掉偶现色带

make-package.bat                 :: 一键打包分享（脱敏 + 压缩，默认放到 P_rojects 根目录）
```

命令行等价写法（必须在仓库根目录执行）：

```bat
python -m erranim.player
python -m erranim.player --audio                 :: 实时音频
python -m erranim.audiotrack --out out\demo.wav  :: 离线音轨 + ffmpeg 后期
python -m erranim.film --record out\demo.jsonl --out out\demo.mp4 --audio out\demo.wav
python -m erranim.selftest
python -m erranim.audio --test bed               :: 恒定噪声 + 一个个打断模式
python -m erranim.player --list  :: 看段落表与语料库统计
```

## 依赖与安装

**跑终端 demo：零第三方依赖。** 只用 Python 标准库，Python 3.9+ 即可
（本机实测 3.11.9）。不需要 curses（本机 Python 没有 `_curses`，代码刻意避开了它）。

**出片额外需要**：`Pillow`、`numpy`，以及 `ffmpeg` 可执行文件。

| 组件 | 需要什么 | 本机现状 | 安装（如缺） |
| --- | --- | --- | --- |
| 终端播放 | 仅标准库 | ✅ 3.11.9 | — |
| 出片 | Pillow `>=10` | ✅ 12.3.0 | `python -m pip install "Pillow>=10"` |
| 出片 | numpy `>=1.24` | ✅ 2.4.6 | `python -m pip install "numpy>=1.24"` |
| 出片 | ffmpeg（含 libx264/libass） | ✅ `ffmpeg` | 已在 PATH；也可 `--ffmpeg <路径>` 或设 `FFMPEG` |
| 采集语料库 | PowerShell `Get-WinEvent` | ✅ pwsh 7.6.4 | Windows 自带 |
| 改跳杀字样 | Pillow（仅开发期） | ✅ | 见 `tools/make_bigtext.py` |
| 可选 | wcwidth `>=0.2.13` | ❌ 未装 | `python -m pip install "wcwidth>=0.2.13"` |

关于可选的 `wcwidth`：宽字符处理用的是标准库 `unicodedata.east_asian_width`，
对本项目的文本（CJK + ASCII）已经完全够用，**不装也一切正常**。只有在你要往里
塞 emoji、组合字符、零宽连接符时，`wcwidth` 的宽度判定才更准。

国内网络装不上时用镜像：

```bat
python -m pip install -i https://pypi.tuna.tsinghua.edu.cn/simple "Pillow>=10" "numpy>=1.24"
```

`run.bat` / `film.bat` 会自动优先使用 `.venv\Scripts\python.exe`（若存在）：

```bat
python -m venv .venv
.venv\Scripts\python.exe -m pip install -i https://pypi.tuna.tsinghua.edu.cn/simple "Pillow>=10" "numpy>=1.24"
```

> `.bat` 文件内容刻意只用 ASCII：cmd.exe 按 OEM 代码页解析批处理，
> 里面写中文会把脚本本身弄坏。中文提示交给 Python 输出（UTF-8 + `chcp 65001`）。

## 叙事结构：严重度递增，收尾静默，最后一记跳杀

| # | 段落 | 标题 | 时长 | 内容 |
| --- | --- | --- | --- | --- |
| 1 | `boot` | SCM · SESSION START | 7.0s | 会话开始。一切正常，正常得无聊 |
| 2 | `noise` | SCM · NORMAL OPERATION | 12.0s | 日常噪声里，同一条 `[7000]` 启动失败刷了 10 次，无人处理 |
| 3 | `first_fix` | CORRECTIVE ACTION | 16.0s | 第一次修正**成功**了 —— 让你松一口气，然后它又崩了，第二次卡在 88% |
| 4 | `timeout` | RESPONSE TIMEOUT | 14.0s | 30 秒的沉默。画面真的会卡住 2 秒不动 |
| 5 | `identity` | AUTHENTICATION | 16.0s | 「无法使用当前配置的密码以 NT AUTHORITY\SYSTEM 身份登录」 |
| 6 | `abandon` | NO CORRECTIVE ACTION | 10.0s | `[7034]` 意外停止，**连修正动作都没有** |
| 7 | `cascade` | CASCADE FAILURE | 20.0s | 多器官并发衰竭。满屏同形异码，进度条碎成乱码 |
| 8 | `silence` | （无标题） | 9.5s | 全黑，光标闪烁，两行字 |
| 9 | `jumpscare` | （无标题） | 4.2s | 全屏反白 → 红色立体大字 `SYSTEM HALTED`（随机蒙版遮盖）→ 错位与污渍吃字 → 硬切黑场 |

合计 **108.7 秒**（1.0x）。

每一次崩溃都走完整的**五拍**：宣告 → 失败 → 修正操作（进度条） → 重试 → 结束（×N 计数 +1）。

### 进度条的三级演化

| 级别 | 样子 | 出现的段落 |
| --- | --- | --- |
| **L1 常见简略** | `[########################--]  92%` | 第 2–3 段 |
| **L2 宽字符** | 满宽 `▕██████▓░░░░▏  30.2%`，带残影与扫描头 | 第 4、6 段 |
| **L3 崩坏** | 字符碎裂、有洞、随机断成两段、抖动；百分比变成 `9999999%` / `-0%` / `NaN%` / `∞%` / `1e9%` | 第 5、7 段 |

核心设定：**进度条永远走不到 100%**，或者走到了就清零重来 —— 所谓"修正操作"
本来就是一个不会成功的修复循环。

## 语料库与随机机制

### 问题：原始素材在逻辑上是不成立的

给定的 md 是**去重摘要**：它保留了每条事件的主行，却把紧随其后的具体错误原因
丢掉了。于是屏幕上出现

```
netprofm 服务无法使用当前配置的密码以 NT AUTHORITY\NetworkService 身份登录，错误原因如下:
```

然后什么都没有 —— 一句承诺了原因却拒绝给出原因的话。

### 修复：把真实的多行事件完整取回来

`tools/harvest_scm.ps1` 从 Windows 事件日志采集近 N 天全部 SCM 事件，
按 (事件 ID, 主行, 原因) 去重，保留出现次数与首末时间，写出 `data/corpus.json`：

```bat
pwsh -NoProfile -File tools\harvest_scm.ps1 -Days 30 -Out data\corpus.json
```

本机结果：**1700 条原始事件 → 51 条去重事件，其中 17 条带具体错误原因**。

现在同一条事件的渲染是逻辑闭合的（原因行按真实层级缩进）：

```
[7038] netprofm 服务无法使用当前配置的密码以 NT AUTHORITY\NetworkService 身份登录，错误原因如下:
       内存资源不足，无法处理此命令。
       要确保服务配置正确，请使用 Microsoft 管理控制台(MMC)中的服务管理单元。
```

> 顺带得到整个作品最好的一句：**网络身份服务之所以认不出自己，是因为内存不够了。**

采集回来的原因都是真实的，比编的狠得多：

| 事件 | 服务 | 真实原因 |
| --- | --- | --- |
| 7038 | netprofm / WerSvc / DiagTrack / CDPSvc | 内存资源不足，无法处理此命令。 |
| 7000 | Network List Service | 由于登录失败而无法启动服务。 |
| 7000 | Network List Service（另一例） | 页面文件太小，无法完成操作。 |
| 7000 | inpoutx64 / 连接设备平台用户服务 | 系统资源不足，无法完成请求的服务。 |
| 7000 | Connected User Experiences and Telemetry | 服务没有及时响应启动或控制请求。 |
| 7024 | Routing and Remote Access | 请求的名称有效，但是找不到请求的类型的数据。 |
| 7006 | ScRegSetValueExW | 拒绝访问。 |
| 7030 | AMD User Experience Program Data Uploader | 服务标记为交互服务。但是系统配置成不允许交互服务。 |

`data/corpus.json` 不存在时，全部退化到 `records.py` 内嵌的兜底数据，代码不会崩。

### 随机机制（可开关）

```bat
run.bat                     :: --random off（默认）：只用剧本素材
run.bat --random on         :: 背景噪声与额外错误事件改为从语料库结构化采样
```

打开后：

1. **背景噪声**读真实事件，并按真实出现次数加权 —— 但权重封顶到 30，
   否则 `7040`（本机 1700 条里占 1574 条）会把背景刷成同一句话。
   每 5 行留一行给带数字的诊断模板，避免长文过于单调。
2. **每个段落额外插入若干"有逻辑的错误链"**：`Corpus.sequence()` 按严重度
   阶梯递增地采样（先在低严重度里挑，越往后越往高严重度走，但保留随机回落），
   像一次真实的故障演进，而不是把事件随便撒出去。

全部由 `--seed` 决定，可复现。

## 故障效果库

全部是**时间的确定性函数**（同一 `t` 必然得到同一画面），所以跳段、重放、
出片永远一致。随机数按 (效果, 起始时刻, 当前时刻量化到 15Hz) 播种，
绝不缓存 RNG 实例。

| 效果 | 做什么 |
| --- | --- |
| `char_noise` | 撒随机故障字符，密度随效果进度衰减 |
| `homoglyph` | **同形异码**：把 ASCII 换成西里尔/希腊里长得一样的字母。`Error Reporting Service` → `Εrrоr Rероrting Seгvіcе`，肉眼几乎看不出，但文本已经坏了 |
| `row_flip` / `row_shift` / `row_dup` | 整行镜像 / 位移 / 复制 |
| `row_invert` | 整行反白 |
| `scanlines` | 隔行压暗，模拟扫描线 |
| `escape_literal` | 把转义序列当**字面量**打在屏幕上（`ESC[2J`） |
| `dead_pixels` | 随机亮点/坏点 |
| `blackout` / `flash` / `dim_all` / `bright_rows` | 局部熄灭 / 全屏闪白 / 整体压暗 / 整行提亮 |

### 信息层（htop 面板）也要吃故障

早先信息层是**免疫**的：故障只作用在日志区，于是画面上唯一一直"正常"的东西
反而是最不可信的那块仪表 —— 一台正在死的机器，它的监控面板不可能还那么整齐。

| 效果 | 做什么 |
| --- | --- |
| `panel_noise` | 面板上撒噪声字符，密度随 k 增长 |
| `panel_corrupt` | 把已有的字换成低墨量的垃圾（`.` `·` `:` `/`）—— 像信号丢了，而不是被砸了 |
| `panel_garbage` | 在资源行上糊一串十六进制"读数" —— 计数器开始吐垃圾 |
| `panel_invert` / `panel_dim` | 面板整行反白 / 整体变暗（仪表读数掉下去） |

**资源读数本身也会崩**。这是关键的一半：如果日志已经烂了，而 CPU/GPU/RAM
三个数字还安安稳稳地按正弦曲线走，那它们就是假的。`panel_sev()` 把信息层故障
的强度传给 `res_values()`，读数按它被拉向垃圾值（CPU 疯跳、GPU 掉零、RAM 顶死），
仍然是确定性的（种子 = 段落种子 × 7919 + 量化时间）。

节奏是**设计过的**：故障表集中在 `scenes.PANEL_GLITCHES` 一处，一眼能看出它
在递增 —— boot 1 次、noise 2、first_fix 3、timeout 3、identity 4、abandon 3、
cascade 13 次，整整一屏的仪表在最后那段彻底不可信。

**作用范围是严格分开的**：信息层故障只动顶部三行（资源行 + 表头 + 分隔线），
日志区一个字符都不碰（自检里有这条断言）。

### 跳杀（第 9 段）

几个来回之后定下来的做法。**核心矛盾**是：既要"同一行字被复制了七份"，又要
"始终认得出写的是什么"。前几版全毁在后半句上。

**字体**：Arial Bold（不是 Arial Black）。字重中等才有地方做描边区分；
正体、不做斜切拉伸 —— 之前那版斜体+重体，放大后字形完全不可辨认。

**主字 / 副本必须拉开距离**。这是整段最容易做错的地方：副本间隔比字宽小的
时候（早先那版步长只有 0.09~0.145 个字宽），七个副本会叠成一坨红，
谁的字形都认不出来 —— 看着像"画面糊了"，而不是"这行字被复制了七次"。
现在的间隔是 **0.62~0.75 个主字宽度**，代价是后几个副本跑到屏幕外面
（这是允许的，"最后一个允许出画"本来就是设计的一部分）。

| 元素 | 颜色 | 描边 | 亮度 |
| --- | --- | --- | --- |
| 主字 | 亮红 `0xE81B1F` 实心 | 浅红 `0xFFB4AC` 紧贴一圈 + 加性辉光 | 始终 100% |
| 副本 | 暗红 `0x6E0C11` 实心 | 无 | 逐个递减 `0.78^i` |

**走位是动画，不是一次摆好**：主字从右下往左上**滑**过去（缓出），
每经过一个副本位就"盖"一个章。所以副本是一个一个被留下的，观众看到的是
"这行字一边走一边掉副本"，而不是"一开始就有七份"。

**一个严重度标量驱动全部**：`sev(t) = k^2.6`（前一半时间只走到 16%，
最后 20% 走完一半以上）。副本的缺墨量、色边偏移量、背景撕裂带的数量、
最后显像管的塌缩，全部是它的函数。**指数 2.6 是"逼上来"的感觉来源** ——
早先每个效果各走各的线性时钟，结果只是一堆东西同时缓慢变化。

**收尾是显像管断电**：最后 0.28 秒画面被压进一条越来越窄的横带
（高度 `h/(1+13u)^1.3`，中心固定），带边缘拖亮/暗回响，最后剩一条亮线。
这是全片最"机器死了"的一下，比单纯闪一下白强得多。

**向下拖影（瀑布）**：主字**落位之后**，把它一列一列往下拉出屏幕。

- **只给最后那个位置做** —— 走位那一路不留瀑布（`drip_k()` 在落位前恒为 0）。
- **每列各自淌**，不是整体拉伸：整体拉伸会得到一条整齐的斜切，像加了 shear
  滤镜。这里每一列都从**它自己字形的最低那个像素**开始往下画，字母本身
  高低不齐，所以起点天然是错的。
- **只做一件事**：连续往下画到屏幕底，横向沿路缓慢随机漂移（每列有自己的
  倾向，每 8 像素抖一次）。没有断点、没有跳变、没有长短之分 —— 简单才像淌。
- 错位是**走出来的**：列与列慢慢岔开，所以逐行的宽度必然在变，也不会是
  等量平移。自检里有两条针对性断言（"逐行宽度在变"、"最小 x 的差值不是常数"）。
- 画在主字**之前**：起点高的那些列会经过下面的字，压在字后面才像
  "墨从字缝里淌出来"，也不会把字糊掉。

终端那条路同理，只是用**深浅三档**代替渐变（贴着字身用字身色，往下换暗红，
最远用更暗的一档）。

**画法**用 `--scare-style` 选：`echo`（主字+副本，默认）/ `solid`（只有主字）/
`outline`（全描边线稿）。

时间轴：`0.00` 全屏反白 → `0.10` 大字从右侧滑入 → `1.15` 落位到左上 →
`2.27` 起显像管塌缩 → `2.55` 二次反白（**按不规则门闪三下**，不是一块白板）→ `2.70` 全黑。

**字体的电子感**来自四件事，缺一不可 —— 之前那版是平滑实心填充，
看起来像印在纸上：

| 手段 | 做法 |
| --- | --- |
| **硬边** | 填充直接二值化，不做抗锯齿软过渡。软过渡就是"纸质"的根源 |
| **扫描线** | 填充内部按行打条纹（隔行压到 0.52），像荧光屏的行扫描 |
| **辉光** | 整体模糊一份做加性叠加，当作荧光余辉 |
| **色边** | 红通道右移、蓝通道左移 —— 显像管没对齐。只在主字上做，范围一小是"没对齐"，铺满全屏就变成"看不清" |

**背景那层**是横向撕裂 + 丢像素，颜色**比底色亮**（暗红/暗灰）。
位置按固定顺序推进（随机只用来定顺序，推进交给严重度），所以是"损坏在爬过画面"，
而不是"损坏在原地闪"。往黑里再压黑等于什么都没画。

### 终端层 vs 视频层

跳杀有两套实现，共用同一份布局（短语、副本偏移、走位、时间轴、严重度）：

* **终端**：只能画字符，用**实心块**（`█`）拼出字形 —— 不再用线字符，
  一格宽的线在终端里细得看不清。亮红实心 + 黑缝 + 暗红实心副本。
* **视频**：直接画到像素上，真正的矢量字（实心填充 + 浅红紧密描边 + 电子质感 + 塌缩）

两者有一个必须注意的差别：**终端字符格是 10×22 像素（高是宽的 2.2 倍）**。
拿同一个 scale 去乘源图的宽和高，字会被纵向拉长 2.2 倍。而且按像素等比缩
出来的字在终端里只有三点几行高 —— 等于认不出。所以终端那条件**字高优先**
（`MIN_ROWS = 10`），宁可少留几个副本。

录制时**刻意不把跳杀写进字符网格**，两版不会叠在一起。
出片时顺序是**先画解码失败的宏块、再把矢量字压在上面** —— 反过来的话
宏块会盖在大字上，最后认不出写的是什么。

## 逻辑帧：为什么不是 60fps

画面是时间的**纯函数**，播放器只做一件事：算出「下一个画面会变的时间点」，
然后睡到那一刻。不动就一帧都不渲染。

实测（`python -m erranim.player --bench`，132×42）：

```
总时长        108.70 s
实际渲染帧数  1155 帧（平均 10.6 帧/秒）
渲染+编码     0.96 ms/帧 平均，最差 5.66 ms
输出量        2.8 KB/帧，合计 3.1 MB
```

对比"每帧都渲染"的 30fps 做法：3261 帧 → **1155 帧**，而且逐帧 CPU 只占
60fps 预算（16.7ms）的 5.8%。

由此得到两个性质（`erranim.selftest` 里有断言）：

1. **倍速无关**：循环是"跳到下一个变化点"而不是"按固定步长累加"，
   0.4x 和 10x 访问的是**同一批帧**，录下来的帧序列与速度完全无关。
2. **确定性**：同一时刻反复渲染、甚至重新构建整套场景再渲染，结果逐格一致。

第 8 段（静默）只有 **二十几帧 / 9.5 秒 ≈ 2.4 帧/秒** —— 大部分时间屏幕上只有
一个闪烁的光标，那就只在这一个像素变化时才渲染。

每一段的日志区都做了**预热**（在时间轴负半轴预置噪声行），所以段落一开场
日志就是满的，不会先空一大片再慢慢填。

## 出片（A 线）

**终端和视频共用同一个渲染核心**：`Grid`（宽字符网格）→ 两条出口，
一条是 ANSI 差分流给终端，一条是结构化帧数据落盘给视频。改一处两边都变。

```
player --headless --record out/demo.jsonl     # 930 个逻辑帧
        ↓
film.py  numpy 合成 → 原始 RGB → 管道喂给 ffmpeg → out/demo.mp4
```

- 每帧在成片里的停留时长 = 它的真实停留时长；用**累计目标帧号**补帧，
  不做逐帧四舍五入，所以没有累积漂移（108.7 秒就是 108.7 秒）。
- 走 stdin 管道喂 rawvideo，不落中间图、不用 concat 时长。
- 同一个 `demo.jsonl` 可以反复出片：换字号、换帧率、换质量、换后期，
  **不用重跑动画**。

### CRT 后期链（`--no-crt` 可关）

从**性能**和**可读性**两头考虑过：

| 环节 | 做法 | 说明 |
| --- | --- | --- |
| 隔行扫描线 | `drawgrid` + `y='mod(floor(t*2),2)'` | 相位按 2Hz **周期性翻动**，确定性，不是随机抖 |
| 逐行扫描滚动带 | `drawbox` 的 `y` 走表达式，约 20 秒一趟 | 暗带 + 前沿亮线。它决定成片的帧率下限，所以走得很慢 |
| 偶现色带 | 初始化时按种子生成 7 条事件表，之后每帧只复用 | 长度 0.07–0.34 秒、透明度 0.06–0.15，保守 |
| 解码失败特效 | **numpy 帧上施加**，不走 ffmpeg | 规整的宏块损坏：缺失块/错位块/纯色块 + 横向切片位移 + 抽条压暗 |
| 亮度 | `eq=contrast=1.02:brightness=0.045:gamma=1.06` | **原来 brightness 是负的**，加上重暗角，屏幕边缘的字根本看不清 |
| 颗粒 | `noise=alls=5:allf=u` | **静态**颗粒：逐帧噪点费 CPU，还会让 x264 完全压不动 |
| 暗角 | `vignette=a=PI/7` | 从 `PI/4.2` 大幅减弱，边缘留得住字 |

### 别让 CPU 变成暖气

`h264_amf` 只接管编码，**滤镜仍然全在 CPU 上**。实测 10 秒成片的 ffmpeg CPU 时间：

| 配置 | 总 CPU | 墙钟 | 并行度 |
| --- | --- | --- | --- |
| 无 CRT、无特效 | 1.47s | 0.75s | 2.0 核 |
| 有 CRT、无特效 | 5.16s | 2.21s | 2.3 核 |
| 有 CRT + PNG overlay 特效 | **16.3s** | 2.65s | **6.1 核** |
| 有 CRT + numpy 特效 | **3.7s** | 2.23s | **1.7 核** |

三路 `-loop 1` 的 PNG `overlay` 一个人就加了 11 秒 CPU，把并行度顶到 6 核 ——
这就是"GPU 只 50%、CPU 却 100°C"的来源。改成 numpy 叠加后总量降到 1/4、
峰值并行度降到 1.7 核。另外 `--filter-threads`（默认 4）给滤镜线程数设了上限，
宁可慢一点也不要把峰值功率顶上去。

### 编码器

`--codec h264|hevc|av1`，各自硬件优先、软件兜底：

| 家族 | 硬件 | 软件兜底 |
| --- | --- | --- |
| h264 | `h264_amf` | `libx264` |
| hevc | `hevc_amf` | `libx265`（`-tune grain`） |
| av1 | `av1_amf` | `libsvtav1` |

跳杀那段（噪声最重，105–108.7s）实测：**h264 172KB / hevc 213KB / av1 139KB**
—— AV1 对颗粒感内容确实最省，比 H.264 少约 19%。

> 坑：**AV1 的 QP 量程是 0–255，H.264/HEVC 是 0–51**。一开始给 AV1 也传 20，
> 等于快无损，码率直接翻倍。

```bat
python -m erranim.film --record out\demo.jsonl --out out\demo.mp4 --codec av1
python -m erranim.film --record out\demo.jsonl --out out\x.mp4 --start-seconds 105 --limit-seconds 4
python -m erranim.film --record out\demo.jsonl --out out\x.mp4 --benchmark --limit-seconds 10
```

## 音频：**一条恒定噪声** + 不同节奏的打断

erranim/bed.py（噪声 + 打断模式）+ erranim/dsp.py（DSP 原语）
+ erranim/audio.py（三层总线）+ erranim/director.py（事件 → 声音）。

四版走过来才定下这个架构：

| 版本 | 做法 | 问题 |
| --- | --- | --- |
| v1 | 每个故障一个**合成音效**（正弦 + 白噪声） | 干净得像数学题，是个"音效包" |
| v2 | 每个故障一个**对底噪的操作**，串行加性叠加 | 两个故障会互相调制；底噪被红/黄音效的动态处理带着抖 |
| v3 | 一条噪声 + **并行**的独立声部（各自滤波/梳状/降位深） | 扫频太抢戏；故障音仍然像"效果器演示" |
| **v4** | 一条**恒定**噪声 + 不同节奏的**打断** | —— |

用户最后一轮把声音设计收窄成了一句话：

> 一个几乎恒定的白噪声，不同的故障只是**暂停的方式**略有区别
> （比如骤停爆音，或者停顿一下、放一下、再卡一下、再正常）

所以 v4 **没有扫频、没有滤波器扫、没有降位深、没有梳状延迟**：

`
恒定噪声 ──► [门] ──► 底噪电平 ──► 噪声总线 ──┐
              ▲                              ├──► 相加 ──► 输出
              └── 每个故障 = 一串             │
                  (时长, 门开度, 爆音量)       │
                                          警告总线 ──┘
`

- **门开度 < 1** = 噪声被压下去 / 掐掉（这就是"暂停"）
- **门开度 > 1** = 噪声"放一下"（回来的时候比正常响一点）
- **爆音量** = 段首那一下"啪"。它用的是**同一条噪声**乘一个 3.5ms 的指数包络，
  所以不是外挂音效，而是"这一刀切下去本身的声音"
- 门是**所有活跃故障的乘积**，所以两个故障叠在一起只会切得更深，不会互相调制

### 为什么不要扫频

底噪的职责是"在那儿"。它会扫频的时候，人就一直在等它扫回来 —— 那是主角的
行为。取消之后它才真的成了背景，而**打断**才成了唯一的表达手段：你注意到的
不是噪声本身，而是它什么时候停、停多久、怎么回来。

自检里有一条硬断言：把噪声切成 6 段，**各段的谱重心波动必须小于 6%**
（实测 4.8%）。扫频要是回来了，这条会立刻挂。

### 噪声的循环周期

四个噪声缓冲的长度取四个**互质的素数秒**：**41 / 43 / 53 / 59**。
合起来的循环周期是它们的最小公倍数 —— 约 **46 小时**，所以在这片子里
听不到任何重复。单个缓冲之间靠 0.25 秒交叉淡化接回开头，接缝听不出来。

底色本身：粉（嘶）+ 布朗（隆）两种噪声叠，加上单样本的**噼啪**脉冲和
50Hz 工频嗡鸣。噼啪是底噪里唯一"活着"的东西 —— 滤波器不扫了，电平也不
呼吸了。截止固定在 3.6kHz，只有一层轻微的 tanh 软削波。

### 打断模式

| 模式 | 节奏（门开度序列） | 对应画面 |
| --- | --- | --- |
| 	ick | 一个 14ms 的**突起**（1.75×） | 日志底噪、闪烁 |
| skip | 停 45ms | 坏点、行复制 |
| stutter | 停 38 → 停 52 → **放** 62(1.3×) → 停 30 → 正常 | 字符噪声、行位移 |
| halt | 一刀切到底（爆音 1.0）→ 停住 → "哒"地回来 | 黑屏（停多久跟故障时长走） |
| dropout | 掉到 0 → 0.45 → 慢慢回到 1 | 压暗、停滞 |
| licker | 门按 26Hz 开合 0.34 秒 | 反白、扫描线 |
| impact | 先空 8ms → 轰回来（带 41Hz 冲击） | 闪白、跳杀 |
| deny / 
ote | 停→放→再卡 / 轻轻压一下 | 红/黄日志（只在关掉警告音时用） |

"停顿一下、放一下、再卡一下、再正常" 就是 stutter 的字面翻译。

### 红/黄警告是独立的一层

用户原话："红黄警告换回去，独立于其他的声音。"

所以红/黄日志用的是**系统经典音效**（Windows Critical Stop / Exclamation），
走**自己的总线**：

- 它们不进噪声的门 —— 噪声停顿时警告照响；
- 噪声也不被它们影响 —— 自检里有一条断言：连发 6 次红黄警告，
  **噪声那一层逐样本不变（偏差 0.000000）**。

上一版把两者一起送进同一个 	anh，于是每次警告一响，软限幅就把整条噪声
一起压下去 —— 听起来像"底噪被吓了一跳"。现在两条总线各自限幅，只在最后相加。
--no-warnings 可以关掉警告音，关掉之后红/黄日志会改在噪声上留一道打断。

### 骤停

第 8 段"静默"从第 **95.0 秒**开始，整条音频被掐死（4ms 斜边，只为不爆音），
**连打断模式也清空**。之后 9.5 秒一点声音都没有 —— 画面还在打
"系统已就绪。/ 未检测到任何用户。"，而声音已经死了。实测那一段是
**逐样本 0.000000**。第 104.5 秒跳杀：解冻 + impact，死寂之后的那一下。

时间冻结那两秒用的是同一个机制（hold_bed）：把噪声的门按住。
**不是加音效，是抽掉声音。**

`at
python -m erranim.audio --list                  :: 模式、映射、素材
python -m erranim.audio --check                 :: 免声卡自检（无扫频/总线隔离/骤停）
python -m erranim.audio --test bed              :: 恒定噪声 + 一个个模式过一遍
python -m erranim.audio --test bus              :: 总线隔离：连发红警告，盯噪声
python -m erranim.audio --wav out\audio         :: 导出 wav 离线试听
python -m erranim.player --audio                :: 播放时开音频
python -m erranim.player --audio --no-warnings  :: 关掉红黄警告音
`

### 出片的音轨：离线渲染 + ffmpeg 后期

终端实时那条路只能听**干声** —— 混响、压缩、限幅都会引入延迟，`loudnorm`
更是必须看完整个流才算得准。所以出片单独走一遍：

```bat
python -m erranim.audiotrack --out out\demo.wav        :: 渲染 + 后期
python -m erranim.audiotrack --out out\demo.wav --no-polish   :: 只要干声
python -m erranim.film --record out\demo.jsonl --out out\demo.mp4 --audio out\demo.wav
```

两条路共用 `director.py` 的事件逻辑，所以**内容完全一致**，只是出片那份多了一层
空间感和动态处理。后期链（全部实测过）：

```
firequalizer   60Hz 以下软切 + 4kHz 以上渐进滚降（-4dB@8k，-15dB@20k）
               ↑ 这一条就是"模拟味"和"数码味"的分界线。
                 数码味的特征恰恰是 20Hz–20kHz 平直。
equalizer      50Hz 抬（机箱）、180Hz 收（去浑）、3.2kHz 抬（临场）
acompressor    压住动态，让"停住"和"炸开"的差距更明显
aphaser        极慢的相位漂移 —— 磁带/显像管那种"不稳"
aecho          几个稀疏的早期反射，做一个假房间
stereowiden    展宽
asoftclip      4 倍过采样的 tanh 软削波（过采样之后不会混叠）
alimiter       -1dBFS 限幅
loudnorm       统一到 -16 LUFS
```

三个容易踩的单位坑记在这：`acompressor.threshold` 和 `alimiter.limit` 是**线性**的
（0.09 ≈ -20.9dB，0.891 = -1dB），`acrusher.bits` 是整数，`bandpass` 没有 `poles` 选项。

## 屏幕上的信息栏

顶栏只留**真实日志里会有的东西**：左边时间戳，右边段标题。

原来还有 `REC ●`、`UPTIME`、`×N` —— 那些是自己加的装饰，放在一台机器的诊断日志上
会出戏：`REC` 是摄像机语汇，`×N` 是"去重统计"的产物，真实日志里不会出现。
重复次数改成用日志本身表达（同一条错误行连续刷 10 次，这比一个计数器更压迫）。
调速反馈挪到底部状态行；状态文字（`正在验证凭据。`）保留。

## 打包分享

```bat
make-package.bat                 :: 默认输出到项目上一级目录（P_rojects 根）
make-package.bat --out-dir .     :: 输出到当前目录
```

写不到目标目录时会**自动退回项目目录**，不会失败。

### 打包前会做脱敏

语料是从**真机**采的，源码里也引用了原始素材的位置，这两类必须处理。
脚本只改**打包副本**，工作区原文件不动：

| 处理对象 | 做什么 |
| --- | --- |
| `data/corpus.json` 的 `meta.machine` | 计算机名 → `REDACTED` |
| 语料库里所有值 | 真正的绝对路径（`X:\...`、`\\server\share`）→ `<路径已隐去>` |
| `records.py` / `README.md` | 指向原始素材个人目录的路径 → `<素材原始目录>` |

脱敏只匹配**带盘符的绝对路径**，所以 `NT AUTHORITY\NetworkService` 这类日志正文
不会被误伤（这一点有专门验证）。脚本每次都会打印它改了什么。

> 仍然保留的是 Windows 服务名与错误文本本身。像 `Overlay Tunnel Service`、`Overlay Tunnel Service`
> 这类第三方服务名会透露你装了什么软件 —— 它们也是这个作品真实感的来源。
> 如果你觉得这些也要去掉，直接文本替换 `data/corpus.json` 与 `erranim/records.py`
> 里的名字即可，代码不依赖具体名字。

包里另附一份 `先读我.txt`，写给收到的陌生人看。

## 已知边界与后续

- **实时音频是干声**。终端播放那条路不做混响/压缩/限幅（会引入延迟，
  `loudnorm` 更是必须看完整个流）。出片那条路有完整的 ffmpeg 后期链。
  如果想让终端也好听，可以加一层"流式安全"的 ffmpeg 滤镜
  （`tremolo` / `aphaser` / `asoftclip` / `acompressor` 这些不依赖全局信息的），
  但 `loudnorm` / `areverse` / `afir` 无论如何都得留在离线那一步。
- **打断模式的门是相乘的**。两个故障同时发生时只会切得更深，不会变成
  "两个声音"。这是有意的（你听到的永远是同一条噪声），但代价是没法做
  "两个不同质感的声音同时响"。
- **语料库目前是 30 天窗口**。`tools/harvest_scm.ps1 -Days N` 可以改；
  也可以把 System 以外的日志（Application、Microsoft-Windows-Kernel-Power 等）并进来。
- **素材可以再往下挖**。这台机器真正的那次崩溃是"帧重复累积 + 不限帧率，
  内存以 150MB/s 上涨，虚拟内存到 77.4GB" —— 和语料库里
  `netprofm` 那条「内存资源不足，无法处理此命令。」是同一条线，
  之后想加一段"内存持续上涨"的节拍，现成的钩子已经在了。
- **中文/英文混排**：日志正文保留中文原文（恐怖感来自那种官僚语气，也是"真实机器
  日志"的可信度来源），机器界面、段落标题、**跳杀大字**全用英文 —— 中文块字出戏。
  未适配中文的场景直接上纯英文。
- **方块字依赖字体覆盖**：终端里的 `█▀▄` 需要等宽字体有对应字形。
  Consolas / Cascadia Mono / 更纱黑体都有；若你的字体缺字而回退到 CJK 字体，
  这些字符可能被渲染成双宽，跳杀大字会错位。视频侧不受影响（自己画的矩形）。
- 终端建议 **Windows Terminal + 等宽字体**，窗口放大到 118×32 以上。
  背景色由程序逐格写入，所以浅色主题也不会翻车。
